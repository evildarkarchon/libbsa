2 · A target format module for packing

Worth exploring in-process

tools/cli/main.cpp:55-157, 580-754 · tests/compat/bridge.cpp:224-300 · tests/package-consumer/main.cpp · benchmarks/libbsa_benchmarks.cpp · include/libbsa/writer.hpp

Before · every caller writes the four-way dispatch

Each caller also restates the capability rules by hand: TES3 cannot compress, DX10 has no raw mode and no per-entry policy.

After · callers learn one interface

The four writer classes stay as they are. The module is additive.

Problem
Choosing a target, knowing what it supports, and driving the matching writer is written out in full in two callers and in part in two more; in main.cpp the four pack functions are ~95 lines of copy with one field name changed.
Solution
One public module resolves a target format to its capabilities and to a writer with a single add-and-write interface.
  • Leverage: one interface, four call sites
  • Locality: capability rules stated once
  • Pack logic becomes unit-testable
  • CLI loses its three-enum descriptor
Tension with AGENTS.md. “Keep public headers minimal.” This adds public surface, and family-only options (embedded names, DX10 chunk size, Starfield header fields) resist a single shape. That is the question to grill.

The placement plan is already a glossary concept for DX10 and is where 12 of the 22 tests point. It is the one internal seam with a name worth keeping stable.

Problem
Every family already has one write_<family>_archive interface, but the tests cross three unnamed seams underneath it, so every stage refactor rewrites them.
Solution
One module runs the stage sequence for all four families; tests cross it at the write interface or at the placement plan, and nowhere else.
  • Tests survive stage refactors

Observable behaviour. Preamble order differs today: TES4 validates entries before resolving its profile and documents that as intentional; BA2 resolves the profile first. One home means deciding whether that difference is kept as a parameter or removed.

5 · Bring TES3 onto Stored Payload

Worth exploring in-process

src/formats/bsa/tes3_bsa_{prepare,layout,serialize}.cpp · src/detail/payload_placement.hpp:69-119, 146

Before · a side door for one family

The size-only lane brings a variant subject, an optional payload index, and a throwing take_payload precondition. TES3 also reads each disk source twice: once to size it, once to stream it.

After · one lane, four families

Sharing stays disabled for TES3; that policy value is already explicit at the call site.

Problem
Payload Placement carries a size-only lane with exactly one adapter, and TES3 serialization keeps ~60 lines of private streaming with its own source-changed detection.
Solution
TES3 prepares Stored Payloads like the other three families, the size-only lane goes, and serialization emits through the same path as TES4.
  • Placement interface shrinks
  • One source-observation model
  • One adapter was a hypothetical seam
  • Placement order and emission order decouple
Unrecorded decision. Two comments say TES3 “deliberately does not adopt Stored Payload”, but no ADR says why. Find the reason first. If it is load-bearing, this candidate becomes an ADR instead of a refactor.

Top recommendation

Start with 1 · One BA2 record-table materialization

It is the only candidate where the duplication is exact, the files are the hottest on the read path, no ADR is in tension, and the existing GNRL and DX10 reader tests already pin the behaviour that must not move. It also clears the ground for candidate 3.

Already deep, leave alone

Noticed in passing, not deepenings

  • The worker cap 1024 is written three times: parallel_work.cpp:16, main.cpp:80, extraction.cpp:951. No public constant.
  • ba2_archive_source is a virtual interface with one adapter and no test fake.
