# Public API Reality Check

This audit checks libbsa's current public C++20 surface against the coverage matrix, compatibility evidence, consumer documentation, package-consumer smoke source, and public-boundary policy tests. It is intentionally a proof-and-routing document, not a facade design proposal.

## Scope and evidence policy

Default proof means evidence that is reproducible from the repository without local game archives or BSArchPro-generated corpus output:

- Public headers: `include/libbsa/libbsa.hpp`, `archive.hpp`, `writer.hpp`, `validation.hpp`, and `result.hpp`.
- Public support docs: `docs/coverage-audit-matrix.md`, `docs/compatibility-evidence.md`, `docs/api-mainpage.md`, `docs/integration-examples.md`, `docs/target-format-guide.md`, and `docs/thread-safety.md`.
- Package-consumer proof: `tests/package-consumer/main.cpp` and the package-consumer CTest gates described by `tests/unit/target_format_policy_tests.cpp`.
- Public-boundary and documentation policy proof: `tests/unit/public_include_boundary_tests.cpp`, `tests/unit/export_surface_policy_tests.cpp`, `tests/unit/docs_policy_tests.cpp`, `tests/unit/target_format_policy_tests.cpp`, and `tests/unit/validation_api_tests.cpp`.

Optional local game corpora and BSArchPro-derived manifests remain advisory evidence only. They can increase confidence or justify future hardening, but they are not required for default support claims and they do not replace committed legal fixtures, writer-output tests, package-consumer checks, or docs-policy coverage. `TES5Edit/` remains a read-only reference boundary.

This audit applies the current public-API direction: keep `archive_reader`, validation, bulk extraction, `result<T>`, stable `error_code` categories, and family-specific writers as the public core. Do not introduce a broad facade or new public dependency surface unless a real consumer flow cannot be made understandable or safe through docs, examples, policy tests, or a narrowly evidenced helper.

## Sharp-edge guidance coverage

| Sharp edge | Current coverage | Gap assessment |
|---|---|---|
| Archive virtual paths are not host filesystem paths. | `integration-examples.md` keeps archive virtual paths and host paths as separate parameters; public metadata uses string paths rather than host filesystem types. | Adequate. Keep examples from joining archive names directly onto output roots without caller policy. |
| Missing path versus invalid path. | `archive_reader::find` documents invalid syntax as `invalid_argument` and valid absence as empty optional; `contains` exists for bool-only checks. | Needs a short docs clarification comparing `find` and `contains`. |
| Streaming versus in-memory extraction. | `payload_sink` and `extract` are documented and example-backed; `extract_bytes` is present and fixture-proven. | Needs a docs note on `extract_bytes` as convenience, not the default for large or host-output flows. |
| Bulk extraction error shape. | `extract_entries` documents outer setup failures versus per-entry `bulk_extract_entry_result::failure`; thread-safety docs cover factory and sink concurrency. | Adequate, with policy-test reinforcement in T03. |

| Stable machine branching. | `error_code` and `compatibility_warning_code` are stable; messages are human diagnostics. Package-consumer source branches on `error_code`. | Adequate. Docs can repeat that exact messages are not stable. |

## Helper and API gap conclusions

No broad public facade is justified by this audit. The existing public core is coherent:

- `archive_reader` covers open/list/lookup/extraction.
- `payload_sink` and `extract_bytes` cover streaming and convenience extraction.
- `extract_entries` covers bulk extraction without hiding per-entry failure details.
- `validate_archive` and `validation_report` cover validation and compatibility warnings.
- `result<T>`, `error`, and `error_code` provide stable C++20 error branching without exposing C++23 `std::expected`.
- `tes3_bsa_writer`, `tes4_bsa_writer`, `ba2_gnrl_writer`, and `ba2_dx10_writer` expose target-specific write-new flows without leaking private codec, DirectXTex, TES5Edit, or raw parser internals.

No tiny public helper is unavoidable in T01. The most concrete friction is documentation and package-consumer proof granularity, not missing public capability:

1. `find` versus `contains` needs consumer-facing wording.
2. `extract_bytes` needs consumer-facing guidance so callers understand when it is appropriate.
3. BA2 DX10 lifecycle wording should remain prominent and policy-tested because it is intentionally different from the other writers.
4. Package-consumer runtime proof is representative, not every-family archive runtime proof; that is the known `COV-GAP-003` route.

Potential future helpers should be evidence-gated. Examples that are not justified today include a catch-all archive facade, public codec selection objects, public DirectXTex/DXGI types, raw BSA/BA2 flag builders, or broad host-filesystem extraction helpers. Each would add public surface area while failing to close the currently identified coverage gaps.

## Concrete follow-up recommendation

For S02, prefer docs/examples/policy proof over API expansion:

1. Update consumer docs to explicitly compare `find` and `contains`, explain `extract_bytes`, repeat stable `error_code`/diagnostic-message rules, and keep BA2 DX10 writer lifecycle guidance visible.
2. Strengthen package-consumer or policy tests so the public story is enforced by compile/link smoke and docs-boundary checks rather than this prose alone.
3. Leave executable per-variant validation proof to the `COV-GAP-001` route and installed-package every-family runtime proof to the S05 `COV-GAP-003` route.
4. Do not add a facade, public codec objects, public DirectXTex/DXGI types, or speculative compatibility warnings in S02 without new evidence that docs/tests cannot close the consumer flow safely.
