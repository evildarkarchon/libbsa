## Context

BA2 and TES4-family BSA compatibility values are defined repeatedly in parser, writer-preparation, layout, serialization, and fixture-generator code. Several of these literals are on-disk contract values: archive signatures, subtype FourCC values, version numbers, record/header byte widths, compression method identifiers, sentinel values, archive flags, and texture record markers. When one copy changes without the others, libbsa can still compile while parsers, writers, and regenerated fixtures silently diverge.

The change remains internal. Public headers stay unchanged, `TES5Edit/` remains read-only, and no new dependency is needed.

## Goals / Non-Goals

**Goals:**

- Provide one internal constants surface per archive family for compatibility-sensitive on-disk values shared across implementation paths.
- Make BA2 parser, writer-preparation, layout/serialization, and fixture-generator code use the same BA2 constants.
- Make TES4-family BSA parser, writer-preparation, layout/serialization, and fixture-generator code use the same BSA constants where values are shared.
- Preserve generated archive bytes, parser validation outcomes, compression routing behavior, and fixture manifests.
- Document non-obvious constants near their definitions so future changes have compatibility context.

**Non-Goals:**

- No public API changes or installation of the new headers.
- No behavior change to supported archive versions, compression policies, DDS validation, hashing, or path normalization.
- No broad refactor of parser/writer structure beyond replacing duplicated literals with named constants.
- No new archive-format support.

## Decisions

### Internal per-family headers

Add `src/formats/ba2/ba2_constants.hpp` and `src/formats/bsa/tes4_bsa_constants.hpp` with `inline constexpr` constants in the existing internal format namespaces. The headers are included by library sources and generated-fixture tools through the existing `src` include path, but they are not part of the installed public header set.

Alternative considered: keep constants in anonymous namespaces and duplicate comments in each file. That preserves locality, but it leaves the drift problem intact and does not give fixture generators the same source of truth as the implementation.

### Centralize only compatibility constants

Move archive-contract values into the headers when they are shared across parser/writer/fixture paths. Keep purely local algorithm limits, loop bounds, temporary-file retry counts, and error-message-specific values close to the code that owns them.

Alternative considered: move every numeric literal in the target files. That would create noisy constants for implementation details and make the headers harder to audit for actual format behavior.

### Use semantic names, not file-local aliases

Name constants by the on-disk concept they represent, such as BA2 signatures, BA2 subtype FourCCs, BA2 header sizes by version family, BA2 DX10 chunk header size, BA2 cubemap marker values, TES4-family BSA version IDs, archive flag bits, file flag bits, and TES4 size-flag compression toggle.

Alternative considered: preserve every existing local name in the header. That minimizes edits, but it can encode local parser terminology instead of the shared archive concept.

### Preserve comments at the centralized definition

Move or rewrite existing compatibility comments only when the related constant moves. Comments for values such as BA2 `BAADF00D`, DX10 chunk header width, cubemap markers, TES4 embedded-name separator behavior, and TES4 size-flag compression bits should live at the constant or directly at the behavior that depends on it.

Alternative considered: rely on tests as the only evidence. Tests are required, but comments are still useful because these constants are not self-explanatory and often come from Bethesda/BSArchPro compatibility behavior.

## Risks / Trade-offs

- Header overreach can turn implementation details into pseudo-API -> Keep headers under `src/`, do not install them, and centralize only archive-contract constants.
- Fixture generators depending on internal headers can obscure test independence -> This is acceptable here because the generators already use internal hash and compression helpers; compatibility is still verified through generated bytes and parser/writer tests.
- Replacing literals may accidentally alter types or comparisons -> Use typed `inline constexpr` values matching existing declarations and run the existing BA2/BSA test suite plus fixture-generation targets.
- Some constants appear in adjacent layout/serialize code not listed in the initial issue -> Include adjacent writer pipeline files only when the value is the same archive-contract value, otherwise leave local values untouched.

## Migration Plan

1. Add BA2 and TES4-family BSA internal constants headers.
2. Replace duplicated constants in BA2 parser, prepare, layout/serialize, and fixture-generator code.
3. Replace duplicated constants in TES4-family BSA parser, prepare, layout/serialize, and fixture-generator code.
4. Run focused tests for BA2 GNRL, BA2 DX10, and TES4-family BSA parsing/writing, then build fixture-generator targets to catch internal include or type issues.
5. If a replacement changes generated bytes or parser outcomes, revert that specific replacement and investigate before continuing.

## Open Questions

- None known. Implementation should make narrow decisions value-by-value and avoid moving literals that are not clearly compatibility constants.
