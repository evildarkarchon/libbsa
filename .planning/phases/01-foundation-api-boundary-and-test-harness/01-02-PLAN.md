<decision_traceability>
- D-01: Public facade centers on `libbsa::archive_reader`.
- D-02: Phase 1 includes read/open only; writer shells are not added.
- D-03: The open stub accepts host path text via `std::string_view` and returns explicit unsupported/invalid-argument results; stream abstractions are not designed.
- D-04: Public headers include `libbsa/libbsa.hpp`, `archive.hpp`, and `result.hpp`.
- D-05: Opening is explicit through `archive_reader::open(...)` returning `result<archive_reader>`; constructors do not perform fallible work.
- D-06: Unsupported open returns structured errors instead of fake archive metadata.
- D-07: Public Doxygen comments document the Phase 1 stub contract and future intent, not parser behavior.
- D-08: Public declarations use `libbsa`; private helpers may use `libbsa::detail`; no versioned namespace is introduced.
- D-10: Public API naming remains a soft lock for Phase 2 unless concrete issues emerge.
- D-11: Downstream code uses `libbsa::result<T>`, `libbsa::result<void>`, `libbsa::error`, and `libbsa::error_code`.
- D-12: `libbsa::error` contains a stable code plus diagnostic message, and tests assert codes rather than exact messages.
- D-13: `error_code` includes unsupported, invalid argument, I/O error, and format error without a full parser/compression taxonomy.
- D-14: `result<T>` exposes `has_value`, `operator bool`, `value`, and `error`; rich monadic helpers are not required.
- D-15: `value()` on an error result may throw a programmer-error exception while I/O/format failures travel through result values.
- D-16: Result-returning APIs are marked `noexcept` only where practical; allocation/diagnostic construction is not overpromised.
- D-17: Boost.Outcome was investigated and rejected for Phase 1 because a local result type satisfies the libbsa-owned boundary without a dependency-policy exception.
- D-18: Phase 1 uses a plain `libbsa::error_code` enum and does not integrate `std::error_code`.
</decision_traceability>
</context>
