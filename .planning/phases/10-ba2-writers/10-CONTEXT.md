**Status:** Ready for planning

<domain>
## Phase Boundary

This phase delivers production BA2 writing for Fallout 4 and Starfield GNRL and DDS/DX10 archives. It adds BA2-specific writer entry points over the existing plan-then-finalize writer model, supports explicit in-memory and disk-file GNRL inputs, supports in-memory and disk DDS inputs that are analyzed during planning, emits BA2-native headers, records, file tables, hashes, compression metadata, DDS texture records, chunk records, and payload regions, and proves outputs by reopening generated bytes through `open_ba2` and extracting through `extract_ba2_entry`. It does not deliver external corpus/tool comparison, broad malformed archive hardening beyond writer-input validation, texture transcoding or optimization, performance/multithreading, CLI/GUI behavior, in-place mutation, or any changes under `TES5Edit/`.

</domain>

<decisions>
## Implementation Decisions

### BA2 API Shape
- **D-01:** Add production BA2 writer entry points in a dedicated public `ba2_writer.hpp` or equivalent BA2-writer-specific header. This should mirror Phase 9's `bsa_writer.hpp` discoverability and avoid crowding reader-focused `ba2.hpp`.
- **D-02:** Represent memory-backed and disk-backed BA2 inputs with separate public value types. Do not use one variant-like entry with invalid byte/path combinations, and do not add a stateful builder just to mix input sources.
- **D-03:** Use subtype-specific public input types for GNRL payload entries versus DDS input entries. GNRL entries carry ordinary payload bytes/files, while DDS entries carry actual DDS bytes/files that planning analyzes.
- **D-04:** Use plan/finalize operation pairs for BA2 writers, parallel to `plan_bsa_write`, `plan_bsa_write_from_disk`, and `finalize_bsa_write`. Exact function/type names are planner discretion, but the API must preserve plan-owned bytes and caller-owned sink finalization.

### Target Options
- **D-05:** BA2 target selection should use exact variant-safe values for every required target: Fallout 4 GNRL v1/v7/v8, Starfield GNRL v2/v3, Fallout 4 DX10 v1/v7/v8, and Starfield DX10 v3. Do not rely on loose game-name strings or target inference from file extensions.
- **D-06:** Starfield v3 `CompressionMethod` should be selected as an archive-level writer option for Starfield v3 targets. Support method 0 and method 3 only; mixed per-entry compression methods are not allowed because the native field is archive-level.
- **D-07:** BA2 writer options should provide safe target defaults plus explicit per-entry or per-chunk compression policy overrides. Do not infer compression behavior from archive paths or source file extensions.
- **D-08:** BA2 write plans should echo native target fields needed for inspection, including subtype, version, header size, and compression method. Tests and dry-run consumers should not need to parse emitted bytes just to confirm the basic native target.

### Native Preview Detail
- **D-09:** Use subtype-specific preview sections inside the BA2 write plan for GNRL versus DDS/DX10 layout. A single flat entry list is not enough because DDS chunk and mip information is not meaningful for GNRL entries.
- **D-10:** GNRL plan preview should expose full native record and table detail needed for compatibility tests and dry-run inspection: name hashes, directory hashes, `FileTableOffset`, table regions, payload offsets, packed sizes, unpacked sizes, and compression state.
- **D-11:** DDS/DX10 plan preview should expose texture and chunk detail: texture record metadata, DXGI format, dimensions, mip count, array/cubemap state, chunk regions, mip ranges, chunk offsets, packed sizes, unpacked sizes, and chunk compression.
- **D-12:** BA2 deduplication preview should use stable shared data-region IDs plus archive-absolute offsets for both GNRL payloads and DDS chunks. Do not expose public content hashes; Phase 8's digest-neutral public surface still applies.

### DDS Input Handling
- **D-13:** BA2 DDS writer inputs should contain actual DDS bytes or explicit disk DDS files plus archive-virtual paths. Public callers should not supply BA2-native texture descriptors as the normal Phase 10 API.
- **D-14:** DDS analysis and validation happen during planning. A successful plan owns the derived metadata, chunk payload bytes, and stored payload bytes; finalization must not retain or reopen DDS input files and must only stream planned bytes.
- **D-15:** DDS chunking should be automatic in Phase 10. libbsa derives mip/chunk layout from DDS analysis and target rules; do not expose manual native chunk descriptor controls or optional chunk hints unless research proves they are required.
- **D-16:** Malformed, unsupported, or unrepresentable DDS inputs must fail structurally during planning with no partial plan. This includes malformed DDS bytes, unsupported layouts, impossible mip/chunk mapping, and formats that cannot be safely emitted without transcoding.

### the agent's Discretion
No selected area was left to the agent's discretion. The planner may choose exact type names, function names, helper file names, and test organization details as long as the decisions above, `10-SPEC.md`, existing public API patterns, and project constraints are satisfied.

</decisions>

## Existing Code Insights

### Reusable Assets
- `bsa_writer.hpp` / `bsa_writer.cpp`: Strong public and implementation precedent for a dedicated writer header, exact target enum, separate memory/disk entries, disk reads during planning, plan-owned native table bytes, and finalization that only streams planned bytes.
- `writer.hpp` / `writer.cpp`: Reusable plan/finalize concepts, post-policy stored payload ownership, explicit compression routing, dedup region IDs, archive-absolute offsets, checked arithmetic, and first sink failure propagation.
- `ba2.hpp` / `ba2_reader.cpp`: Native BA2 field order and public metadata model for GNRL and DX10 read-back. Writer output should reopen through this code and match its summary, entry metadata, texture metadata, and extraction expectations.
- `ba2_dds_fixture_helpers`: Source-reviewable generated DDS/DX10 archive builders already cover representative texture layouts and compression routes; Phase 10 writer tests can reuse the fixture style and semantic assertions.
- `memory_source` and `memory_sink`: Useful for generated BA2 write/read-back tests and public-header smoke coverage.
- Private compression and texture helpers: Existing deflate, raw LZ4-block, DDS reconstruction, and DDS validation boundaries should be reused or extended without leaking dependencies publicly.

### Established Patterns
- Public APIs live under `include/libbsa/`, private implementations live under `src/`, public headers use Doxygen comments, and source/test files are wired explicitly in `CMakeLists.txt`.
- Archive path strings are archive-virtual paths normalized through libbsa rules; host filesystem paths are only accepted at explicit disk-input boundaries.
- Writer planning owns all bytes and compatibility-critical layout choices before finalization; finalization does not recompute compression, reopen files, analyze DDS data, or retain sinks.
- Native writer plans expose deterministic vectors of table regions, data regions, and entries; dedup sharing is visible through stable IDs and offsets, not public hashes.
- Codec routing is explicit by archive format, entry/chunk compression state, and Starfield `CompressionMethod`; unsupported routes fail instead of trying fallback codecs.
- DDS extraction currently validates reconstructed output before touching the sink; Phase 10 DDS writing should preserve equivalent no-partial-output safety for planning/finalization boundaries.
- `TES5Edit/` is read-only: reference tracing is allowed, but no edits, formatting, source-list inclusion, staging, commits, or submodule pointer changes.

### Integration Points
- Add BA2 writer public surface in `include/libbsa/ba2_writer.hpp` or an equivalent BA2-specific writer header.
- Add production BA2 writer implementation under `src/`, likely separated from `src/ba2_reader.cpp` while sharing private constants/helpers where appropriate.
- Add or extend private texture-analysis helpers so actual DDS bytes/files can be analyzed during planning without exposing DirectXTex or native BA2 descriptors publicly.
- Extend tests with BA2 writer coverage for GNRL and DDS targets, native header/record/chunk assertions, disk/memory input read-back, compression methods, dedup on/off, and structured failures.
- Extend `tests/public_header_smoke.cpp` so consumers can compile BA2 writer target values, GNRL/DDS memory and disk entries, plan/finalize functions, and plan preview metadata without private headers.
- Update `CMakeLists.txt` deliberately for all new headers, sources, and tests.

<specifics>
## Specific Ideas

- BA2 writing should be discoverable as its own production API surface, parallel to BSA writing, not as a generic Phase 8 harness extension.
- Target selection should be variant-safe and exact; avoid game-name strings, path extension inference, or subtype/version combinations that can represent unsupported archives.
- Starfield v3 compression method is archive-level in the native format, so public APIs should not allow mixed per-entry method values.
- Native preview detail is intentionally rich because Phase 10 acceptance depends on byte-level BA2 layout decisions before Phase 11 external corpus validation.
- DDS writing should feel like packaging real DDS files/bytes, not like constructing BA2 texture records by hand.
- Automatic chunking is the Phase 10 default: planner/researcher should find the correct algorithm and expose only derived preview metadata unless a concrete compatibility need requires more.

</specifics>
